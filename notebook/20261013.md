## 4. Bootstrap order: dependencies form a graph

A setup process has dependencies:

```text
System prerequisites
    → package manager
        → runtimes and command-line tools
            → Python tools and shell plugins
                → configuration
                    → verification
```

A command can be installed successfully but remain unavailable if the shell cannot find it.

### What `PATH` does

`PATH` is an ordered list of directories searched for executable commands.

```text
Directory A → Directory B → Directory C
```

If multiple directories contain a command with the same name, the earlier match generally wins.

Useful diagnostics:

```bash
command -v python3
command -v uv
command -v git
```

These answer **which executable the current shell resolves**, which is more informative than knowing that some installation exists.

**Practical note:** Verify setup in a new terminal session too. A running shell may retain an environment established before installation or configuration changes.

## 5. Idempotency: making reruns predictable

A setup script should recover gracefully from partial completion.

**Idempotency** means applying an operation repeatedly has the same intended effect as applying it once.

A simple installation guard:

```bash
if ! command -v uv >/dev/null 2>&1; then
    printf 'uv is missing; installation is required.\n'
fi
```

An existence check alone is insufficient:

| Check | What it proves | What it misses |
|---|---|---|
| Command exists | A command resolves | Version and behavior |
| Directory exists | Something occupies the path | Correct contents |
| Symlink exists | Path is a link | Correct destination |
| Application exists | App bundle is present | Successful launch |

A stronger operation checks the state it actually requires.

**Another distinction:** A script can be safe to rerun while still upgrading software. “Rerunnable” does not mean “nothing changes.”

### Failure handling

Useful script behavior includes:

- Stop when a required prerequisite fails.
- Report which step failed.
- Avoid printing success after an unsuccessful operation.
- Preserve enough information to resume.

The goal is an explainable partial state.

## 6. Dotfiles and symlinks: one maintained configuration

A dotfile is a configuration file whose name begins with a dot, such as `.zshrc`.

A symbolic link points to another filesystem path:

```text
~/.zshrc
    → ~/mac_setup/dotfiles/.zshrc
```

The shell reads through the link to the repository-managed file.

### Why this reduces drift

With copied files:

```text
Repository copy changes
    ≠
Active home-directory copy changes
```

With a symlink, both paths refer to the same maintained configuration.

### What can still go wrong?

- Moving the repository can break an absolute symlink.
- A link may point to an older checkout.
- Another installer may replace it.
- Editing the configuration changes active behavior immediately.
- Existing configuration may contain settings that still need merging.

**Suggested verification:** Check both that the path is a symlink and that its destination is the intended file.

Backing up an existing file preserves recovery options; it does not automatically integrate its useful settings.

## 7. Portable settings, local settings, and secrets

A useful separation is:

| Layer | Examples |
|---|---|
| Shared configuration | General aliases, prompt preferences |
| Local configuration | Machine paths, employer-specific overrides |
| Credential storage | Tokens, private keys, passwords |

Illustrative zsh loading pattern:

```zsh
# Place after shared defaults if local settings should override them.
if [[ -f "$HOME/.zshrc.local" ]]; then
    source "$HOME/.zshrc.local"
fi
```

**Loading order matters.** Later assignments can override earlier ones.

### “Not committed” is not the same as protected

A local file can still contain plaintext secrets. A password manager or credential store can be more appropriate for sensitive values.

Also, `.gitignore` applies to intentionally untracked files. It does not stop Git from tracking changes to a file already committed. [Git ignore documentation](https://git-scm.com/docs/gitignore)

**Practical rule:** Keep reusable configuration in Git, machine-specific values outside shared configuration, and credential handling explicit.

## 8. Python tooling: global convenience versus project consistency

Python tools can have incompatible dependencies. Installing all of them into one shared environment creates unnecessary coupling.

`uv tool install` installs command-line tools into isolated environments and exposes their executables for convenient use:

```bash
uv tool install black
uv tool install sqlfluff
```

These tool environments are separate from project environments. [uv tools documentation](https://docs.astral.sh/uv/concepts/tools/)

Choose according to purpose:

| Need | Appropriate scope |
|---|---|
| Personal command available anywhere | Isolated tool installation |
| Formatter version shared with teammates | Project dependency |
| Specific dbt adapter and dependencies | Project environment |
| Project’s application libraries | Project environment |

**Subtle point:** Isolation prevents dependency conflicts; it does not guarantee that every developer uses the same version.

If formatting output must match CI, record the formatter version with the project rather than relying solely on a personal installation.

## 9. Verification: installation success is only the first layer

A useful verification process checks progressively stronger claims:

| Level | Question |
|---|---|
| Presence | Does the command or app exist? |
| Resolution | Is the expected executable selected? |
| Execution | Can it run? |
| Configuration | Does it load the intended settings? |
| Workflow | Can it perform a representative task? |

For example:

```bash
command -v git
git --version
git config --get user.name
git config --get user.email
```

Each checks a different assumption.

A Git installation can work while commits use the wrong identity. A Python executable can work while resolving to an unintended installation.

### Suggested acceptance checks

- Required commands resolve and execute.
- Dotfiles point to the expected checkout.
- A new shell starts without configuration errors.
- Local overrides load correctly.
- Git identity is appropriate for the repository.
- Missing required components cause a nonzero verification exit status.

A verification script that prints `MISSING` but exits successfully is readable by a human, yet difficult to use reliably in automation.

## 10. Repository colors: explaining the hash and hook

The terminal-color idea combines:

```text
Repository root path
    → hash
        → selected hexadecimal bytes
            → RGB values
                → terminal background command
```

A hash converts an input string into a repeatable output. Here it serves as a stable mapping, not as a security mechanism.

The expression:

```text
byte % 71 + 30
```

maps a byte into the inclusive range `30–100`, keeping color channels relatively dark.

The zsh `chpwd` hook runs after directory changes. Registering a function through `add-zsh-hook` lets it participate without replacing the whole hook mechanism. [zsh function and hook documentation](https://zsh.sourceforge.io/Doc/Release/Functions.html)

### An important correction: path stability ≠ repository stability

If the hash input is an absolute path:

```text
/Users/alice/projects/demo
/Users/bob/projects/demo
```

the inputs differ, so their colors are not guaranteed to match—even if both checkouts contain the same repository.

A deterministic function guarantees:

```text
Same input → same output
```

It does not guarantee:

```text
Same project at different paths → same output
```

For consistent project colors across machines, use a normalized project identifier or explicit color mapping.

Also, different repositories can map to the same color. Treat color as a recognition aid, never as proof of the active project or environment.

## 11. A practical implementation sequence

For a personal setup repository:

1. **Inventory essentials.** Include tools you use broadly; separate project-specific dependencies.
2. **Write the package manifest.** Record what should be installed.
3. **Make configuration portable.** Replace hardcoded machine paths with explicit local overrides.
4. **Add installation and linking steps.** Preserve existing configuration and make reruns predictable.
5. **Write verification alongside installation.** Give each requirement a corresponding check.
6. **Test failure and rerun behavior.** Consider missing prerequisites, existing files, broken links, and partial installation.
7. **Document remaining manual steps.** Authentication, application permissions, and project onboarding may still need attention.

**Personal takeaway:** A useful setup repository defines what my machine needs, applies that configuration predictably, and checks whether the resulting environment can support my work.
