## 1. The experiment: what should change?

The author changes five source rows: one customer update, one order insert, two order-item inserts, and one order-item delete. Fivetran processes six rows, then automatically triggers dbt.

The expected results are:

| Change | Expected reporting result |
|---|---|
| Rename customer `28222` | One customer row with the new name |
| Add an order worth `$115` | Order count rises from 1 to 2; revenue rises from `$1,509` to `$1,624` |
| Delete another customer’s `$300` order item | That customer’s revenue falls by `$300` |

Instead, the renamed customer appears twice, each with `$1,624`, while the deleted item still contributes `$300`. The models ignore Fivetran’s deletion flag. [Article](https://markphammm.substack.com/p/i-rebuilt-my-ingestion-pipeline-with-85c)

## 2. WAL, logical decoding, and replication slots

**WAL — write-ahead log:** PostgreSQL records changes in a log used for durability and recovery.

**Logical decoding:** converts storage-level WAL information into changes a consumer can interpret.

**Replication slot:** maintains a consumer’s position in the change stream and retains resources needed to resume.

**LSN — log sequence number:** identifies a position in WAL. Think “log position,” rather than “row timestamp.”

A slot survives disconnection. That lets a consumer resume, but a stalled consumer can cause required WAL to accumulate. Slot lag and retained storage therefore matter operationally.

Also, logical decoding can resend recent changes after a crash. Consumers must handle replay without producing incorrect duplicates; a change stream alone does not guarantee end-to-end exactly-once processing. [PostgreSQL logical decoding concepts](https://www.postgresql.org/docs/current/logicaldecoding-explanation.html)

## 3. Three identities that are easy to confuse

| Identity | Purpose | Example |
|---|---|---|
| Business identifier | Identifies an entity in the business | `CustomerID` |
| Declared source primary key | Enforces unique, non-null row identity | `PRIMARY KEY (customerid)` |
| Connector-generated identifier | Identifies records for ingestion | `_fivetran_id` |

A column named `CustomerID` does not automatically have a primary-key constraint. A connector cannot necessarily infer your intended identity from column names.

### Why `REPLICA IDENTITY FULL` matters

An update or delete needs enough information to identify the **old row**. PostgreSQL normally uses the primary key as replica identity. Without a suitable key, `FULL` uses the entire row.

```sql
-- Illustrative source configuration:
ALTER TABLE l1_landing.customers
REPLICA IDENTITY FULL;
```

This does **not** create a primary key or enforce uniqueness. It supplies old-row identity information for replication. PostgreSQL describes `FULL` as a fallback when a suitable key is unavailable. [PostgreSQL replica identity](https://www.postgresql.org/docs/current/logical-replication-publication.html)

**Key distinction:** PostgreSQL replica identity and Fivetran’s generated destination identity solve related problems at different layers.
