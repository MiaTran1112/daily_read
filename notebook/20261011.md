## 8. A practical verification walkthrough

These are proposed checks to adapt to the demo. They have not been executed against a connected database.

### Step A — Write expectations before changing data

Record baseline values and expected deltas. Use separate entities for insert/update and delete experiments so one failure cannot hide another.

For each model, write down its intended grain.

### Step B — Verify ingestion independently

Inspect the affected landing records, including metadata:

```sql
SELECT
    CUSTOMERID,
    LASTNAME,
    _FIVETRAN_ID,
    _FIVETRAN_DELETED,
    _FIVETRAN_SYNCED
FROM FIVETRAN_DEMO.POSTGRES_DEMO_L1_LANDING.CUSTOMERS
WHERE CUSTOMERID = '28222'
ORDER BY _FIVETRAN_DELETED, _FIVETRAN_SYNCED;
```

Ask whether each record is active or retired. Raw row count alone cannot answer that.

### Step C — Check current-state uniqueness

```sql
SELECT CUSTOMERID, COUNT(*) AS current_rows
FROM FIVETRAN_DEMO.POSTGRES_DEMO_L1_LANDING.CUSTOMERS
WHERE COALESCE(_FIVETRAN_DELETED, FALSE) = FALSE
GROUP BY CUSTOMERID
HAVING COUNT(*) > 1;
```

Expected: no rows, **if** the source business rule guarantees one current row per customer.

### Step D — Check staging before the mart

```sql
SELECT CUSTOMERID, COUNT(*) AS rows_per_customer
FROM FIVETRAN_DEMO.TRANSFORM.CUSTOMERS_STG
GROUP BY CUSTOMERID
HAVING COUNT(*) > 1;
```

If landing is correct but staging violates the grain, investigate staging first.

### Step E — Reconcile reporting results

Verify all three dimensions independently:

- **Identity:** one row per expected customer.
- **Attributes:** the current name appears.
- **Measures:** order count and revenue match expected changes.

A correct name does not prove correct revenue.

### Step F — Verify automatic execution

Confirm that the completed ingestion triggered the intended transformation job. A manually successful run proves that a job can execute; it does not prove the trigger is connected.

## 9. Turn assumptions into dbt tests

dbt data tests return records that violate an assertion; zero failing records means the test passes. Built-in tests cover uniqueness, nulls, relationships, and accepted values. [dbt data tests](https://docs.getdbt.com/docs/build/data-tests)

Example:

```yaml
version: 2

models:
  - name: customers_stg
    columns:
      - name: CustomerID
        data_tests:
          - not_null
          - unique

  - name: customerrevenue
    columns:
      - name: CustomerID
        data_tests:
          - not_null
          - unique
```

Suggested additional checks:

| Assertion | Failure it can expose |
|---|---|
| Unique `(OrderID, OrderItemID)` in current order items | Duplicate lines |
| Customer references resolve | Orphan orders |
| Mart revenue reconciles to eligible order items | Missing or duplicated revenue |
| Controlled deletion reduces revenue correctly | Broken deletion propagation |

Uniqueness tests can catch duplicate customers, but a single stale order item may violate no uniqueness rule. Reconciliation tests address a different failure class.

## 10. Notes to keep beside the implementation

- **Define deletion semantics:** Does deleting a source record remove it from current revenue, or must accounting history remain?
- **Separate business time from ingestion time:** “Synced recently” does not mean “occurred recently.”
- **Treat re-sync as an ingestion operation:** It cannot repair a model that includes ineligible records.
- **Verify re-sync behavior:** Current Fivetran documentation describes merging snapshots and marking stale records deleted; do not assume re-sync physically clears retained versions.
- **Validate after completion:** Re-sync can expose temporary mixed states while batches load. [Fivetran re-sync behavior](https://fivetran.com/docs/core-concepts/syncoverview/sync-modes/soft-delete)
- **Keep a model contract:** Document grain, key, current/history policy, and expected measure behavior.

**Personal takeaway:** Before trusting a CDC-backed metric, I should be able to explain what identifies a row, what makes it current, and how each join preserves the intended grain.
