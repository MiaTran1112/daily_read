### Mark Pham: I rebuilt my ingestion pipeline with zero infrastructure: Part 1 - Neon Postgres WAL, Snowflake Credential & Fivetran CDC (https://markphammm.substack.com/p/i-rebuilt-my-ingestion-pipeline-with)

1. ELT: Fivetran + dbt
- Fivetran handles extract + load:
    - Neon/Postgres → Snowflake
- dbt handles transformation inside Snowflake.
- dbt does not connect back to Neon.
- raw/source data is loaded first, then transformed in the warehouse.
-> architecture: Neon → Fivetran → Snowflake → dbt

2. Neon
- Neon:
    - a serverless Postgres, used here as the source/OLTP database.
    - example database: fivetran_source
    - contains the SleekMart OMS data across 8 tables.
    - only responsible for storing the source data.
    - Fivetran connects to Neon and moves the data into Snowflake.
- distinction:
    - Neon/Postgres = source database
    - Snowflake = analytical warehouse
    - dbt = transformation layer

3. Why CDC (Change Data Capture)
- simplest ingestion approach would be repeatedly querying source tables to see what changed.
-> problematic for:
    - large tables
    - detecting updates
    - detecting deletes
    - repeatedly scanning data
- CDC captures changes as they happen instead.
- Fivetran uses Postgres's WAL to capture these changes

4. Postgres WAL
- WAL = Write-Ahead Log
- Postgres writes a record of a change to the WAL before applying the change to the table.
- WAL contains the database's history of changes.
- setting wal_level = logical enables logical replication, which exposes changes in a form external systems like Fivetran can consume.
- instead of Fivetran constantly asking "what changed?", it can consume the database's change stream.
