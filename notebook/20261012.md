# Daily Read Deep Dive: Treating a Development Machine as Code

**Reading:** [I got a new Mac and refused to set it up by hand again](https://markphammm.substack.com/p/i-got-a-new-mac-and-refused-to-set)  

**Study goal:** Understand how to turn a personal development environment into something repeatable, inspectable, and testable—and where that approach stops short of exact reproducibility.

## 1. Article recap

The author replaces manual Mac setup with a Git repository containing a Brewfile, shell configuration, editor settings, and four scripts:

| Script | Responsibility |
|---|---|
| `bootstrap.sh` | Install tools and prerequisites |
| `link-dotfiles.sh` | Link shell configuration, preserving existing files |
| `configure-git.sh` | Configure Git conveniences |
| `verify.sh` | Check commands, links, and applications |

Portable configuration goes in the repository; machine-specific settings stay local. Project dependencies are kept separate from the base machine setup. A terminal customization assigns colors based on repository paths.

The main benefit is reducing configuration drift and making changes reviewable. [Article](https://markphammm.substack.com/p/i-got-a-new-mac-and-refused-to-set)

The sections below explain the underlying concepts and suggest improvements; they are study notes rather than an audit of the repository’s implementation.

## 2. Configuration drift: why setup gradually becomes unreliable

**Configuration drift** is the difference between the environment you intended to have and the environment you actually have.

For example:

```text
Setup notes: Python installed through one tool
Actual machine: three Python installations

Setup notes: one Git identity
Actual machine: employer identity configured globally

Setup notes: a reusable alias
Actual machine: alias depends on an old absolute path
```

Manual installation leaves little evidence of why the machine reached its current state.

Version-controlled configuration helps answer:

- What changed?
- Why did it change?
- Which configuration worked previously?
- Can another machine apply the same instructions?

**Important boundary:** Git can restore configuration files. It does not automatically undo installed applications, operating-system changes, or package upgrades.

A setup repository describes and applies part of the environment; it is not a complete machine backup.

## 3. Brewfile: declaring desired tools

A Brewfile lists what should be available:

```ruby
# Illustrative minimal Brewfile
brew "git"
brew "uv"
brew "ripgrep"

cask "rectangle"
```

| Term | Meaning |
|---|---|
| Formula | Package definition, commonly for command-line tools |
| Cask | Definition commonly used to install macOS applications |
| Tap | Additional repository of package definitions |
| Bundle | Homebrew feature that applies a Brewfile |

Useful commands:

```bash
brew bundle --file=Brewfile
brew bundle check --file=Brewfile
```

The first installs missing dependencies and can upgrade existing ones. The second checks whether the declared dependencies are satisfied. [Homebrew Bundle documentation](https://docs.brew.sh/Brew-Bundle-and-Brewfile)

### Repeatable installation is not exact reproducibility

An unpinned package list can install different versions next month. Homebrew explicitly notes that disabling upgrades does not add version pinning or lockfile support.

Distinguish:

```text
Repeatable setup:
    install the intended collection of tools

Exact reproduction:
    reconstruct specific versions and dependencies
```

For ordinary workstation tools, the first may be sufficient. For a project whose results depend on precise dependency versions, keep a separate project environment and dependency lockfile.
