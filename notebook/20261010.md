## 4. What Fivetran’s metadata actually tells you

| Column | Meaning | Analytical use |
|---|---|---|
| `_fivetran_id` | Generated identifier based on row values | Connector identity for tables without a primary key |
| `_fivetran_deleted` | Marks deleted records or retired versions | Determine eligibility for current-state reporting |
| `_fivetran_synced` | When Fivetran last synced the record | Investigate ingestion timing |

History mode uses different metadata, including `_fivetran_active`, `_fivetran_start`, and `_fivetran_end`, and removes `_fivetran_deleted`. Match model logic to the configured mode. [Fivetran system columns](https://fivetran.com/docs/core-concepts/syncoverview/system-columns-and-tables)

### Why one update can produce two destination operations

For a table using generated identity in soft-delete mode, Fivetran inserts the new version and marks the old version deleted. One business update can therefore affect two destination records. [Fivetran soft-delete behavior](https://fivetran.com/docs/core-concepts/syncoverview/sync-modes/soft-delete)

**Important correction to the earlier recap:** `_fivetran_synced` is not a reliable way to pick the current version. Current documentation describes the old version’s deletion being processed after the new version’s insertion; sorting by the greatest timestamp can select the retired record.

Likewise, soft-delete storage is not automatically a complete historical event ledger. Do not assume it preserves every intermediate business state or supports accurate “as of last Tuesday” reporting. Define historical reporting explicitly; Fivetran provides a separate [history mode](https://fivetran.com/docs/core-concepts/syncoverview/sync-modes/history-mode).

## 5. Join fanout: how valid SQL creates wrong totals

**Grain** means what one row represents.

Suppose the intended grains are:

- Customer staging: one row per current customer.
- Order fact: one row per order.
- Customer revenue mart: one row per customer.

Now consider this illustrative example:

```text
Customer staging:
CustomerID | Name
42         | Alice
42         | Alice Smith

Order fact:
OrderID | CustomerID | Revenue
101     | 42         | 100
102     | 42         |  50
```

Joining on `CustomerID` produces four rows:

```text
101 | Alice       | 100
101 | Alice Smith | 100
102 | Alice       |  50
102 | Alice Smith |  50
```

Each order matches two customer records. This is **join fanout**.

Grouping by name yields two plausible-looking `$150` totals. Grouping only by customer ID yields one incorrect `$300` total. Changing the grouping does not repair the join.

**Why common patches fail:**

- `SELECT DISTINCT` retains rows whose names differ.
- `COUNT(DISTINCT OrderID)` can repair the order count while leaving revenue inflated.
- `SUM(DISTINCT Revenue)` incorrectly collapses different orders with equal amounts.

The repair is to restore the intended customer grain **before joining**.

## 6. Filtering deleted records: what the SQL means

For current-state models reading this soft-delete setup:

```sql
WHERE COALESCE(_FIVETRAN_DELETED, FALSE) = FALSE
```

`COALESCE` returns the first non-null argument. Here, the expression deliberately interprets a null flag as false. [Snowflake COALESCE](https://docs.snowflake.com/en/sql-reference/functions/coalesce)

| Flag | Expression result | Keep row? |
|---|---|---|
| `TRUE` | `FALSE` | No |
| `FALSE` | `TRUE` | Yes |
| `NULL` | `TRUE` | Yes |

SQL comparisons involving null generally produce “unknown”; a `WHERE` clause keeps only true conditions. That is why simply comparing a nullable flag to false can discard null rows.

**Modeling note:** Treating null as “current” is an explicit policy. Inspect actual data and connector guarantees rather than assuming every connector produces null flags.

For historical or deletion-analysis models, retaining retired rows may be intentional. The filter belongs to a defined reporting purpose.

## 7. Incremental ingestion and incremental models are separate choices

| Layer | Question |
|---|---|
| Ingestion | Which source changes need transporting? |
| Transformation | Which warehouse results need recomputing? |

dbt incremental models process the subset of rows selected by your model logic. Updating existing results generally requires a suitable key and strategy. [dbt incremental models](https://docs.getdbt.com/docs/build/incremental-models)

**An important extension:** A current-row filter alone is insufficient for some incremental designs.

Imagine yesterday’s target contains an order item. Today that item is marked deleted upstream. If today’s incremental query filters it out, no record reaches the target to remove yesterday’s copy.

```text
Deleted upstream
    → excluded from incoming batch
    → existing target row can remain
```

Deletion propagation needs explicit design: deleting affected target keys, rebuilding affected partitions, or recomputing affected entities.

Aggregates add another dependency: deleting an item may require recalculating its order and customer totals.
